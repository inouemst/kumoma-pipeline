## 1. このプロジェクトの原則（すべての判断の土台）

技術的な指示より、こちらが優先します。

- **上書きしない** — 本文には触れない。案内文は本文の代わりではなく、入口である
- **序列をつけない** — 「傑作」「名作」「代表作」といった評価語を使わない
- **寄生しない** — Wikipedia・文学事典・既存の解説を参照しない。**本文だけを見る**
- **書けないものは、書けないと言う** — もっともらしい嘘を並べるくらいなら、空欄のほうがよい
- **測れないものは、測れないと言う** — 検証していないことを「検証済み」と書かない

最後の2つは、この会話で繰り返し問題になった点です。**都合のよい条件下でだけ動く検証を、動作の証明として報告してはいけません。**

## 4. これまでに判明した罠（同じ穴に落ちないために）

**これは失敗の記録ではなく、地図です。** 一つひとつ実際に踏んだものです。

### 4-1. データ取得

- **`--filter=blob:none` のまま全件処理するのは致命的**。ファイルを読むたびにネットワーク取得が発生する。sparse-checkout（coneモード）＋ `--depth 1` で一括取得すること
- 本文ファイル名は `{作品ID}_{ファイルID}.html` だが、**`{作品ID}.html` という別パターンも実在する**（これを見落として116件を「取得不能」と誤判定した）
- 文字コードは **Shift_JIS**

### 4-2. 本文パース

- 本文の終端は `<div class="bibliographical_information">`。**`bibliography_information` ではない**（タイポに見えるが、これが正しい綴り）。間違えるとクレジットが本文に混入する
- カギ括弧の深さは**行ごとにリセット**する。文書全体で追跡すると、複数段落にまたがる会話で対応が崩れ、本文全体が汚染される（実際にこころで本文まるごと113,161字が「はじまりの一文」になった）

### 4-3. 判定ロジック

- **旧仮名だから文語、ではない**。泉鏡花の代表作は旧仮名だが口語。芥川の新字旧仮名作品も口語。**仮名遣いと文語/口語は独立した軸**
- **会話文比率は戯曲では機能しない**（話者名＋セリフ形式のため「」を使わない）。岸田国士の戯曲でも0.001〜0.028程度しか出ない
- 閾値を1作品に合わせて「検証済み」としないこと（第一段階でこの失敗をした）

### 4-4. 案内文（第1便で判明）

- **固有名詞は本文の表記のまま使う。** 現代表記に直すと本文と一致しなくなる
  - 舞姫の主人公は「太田**豐**太郎」（豊ではない）
  - 「**淺**野和三郎」（浅ではない）
  - 「**亜米利加**」（アメリカと書くと本文に無い）
- **本文にないことを具体化しない。** 本文が「わが國」としか書いていないのに「日本」と書いたケースが実際にあり、ゲートに捕まった
- **本文が短すぎると案内文は書けない。** 36字の警句に60字の案内文をつけると、案内文のほうが原文より長くなる。→ 200字未満は生成対象外

### 4-5. ゲート（第2便で判明）

- **生成側の自己申告に依存するゲートは、ゲートではない。** 第1便では「使った固有名詞を自己申告させて照合」していたが、申告を省略すれば同じ嘘が素通りすることが判明した。**機械抽出（janome）に一本化済み**
- **誤検知を消すために語彙リストへ語を追加してはいけない。** いたちごっこになる。除外は「形の性質」で行う（例：数詞で始まる連続は除外）
- 文末の集計は**表層4文字で数えない**。「る随筆。」「く随筆。」が別物として数えられ、実際は21.6%あった偏りが15.5%に見えていた

## 5. ゲートの現状（`gates.py`）

案内文は**書いたら必ずゲートに通します**。抜き取りではなく全件です。

| 層 | 内容 | 実装 |
|---|---|---|
| 第三層 | 固有名詞が本文に実在するか | janome機械抽出＋数詞除外。**自己申告は使わない** |
| 第四層 | 非流通語（古語）が混入していないか | ブラックリスト方式 |
| 第五層 | 60〜100字／評価語なし／結末示唆なし | 機械チェック |

**実証済みの検証**（`python gates.py` で再現可能）：

- たけくらべの案内文に偽の「吉原」を入れると**確実に弾かれる**（本文に吉原は一度も出てこない。実際は「大音寺前」）
- 試作で混入した5語（廓・楼上・麦酒・従僕・逢引）が**全て検出される**

**残存誤検知率は4.1%**（97篇中4件）。これは実測値としてそのまま受け入れており、パッチは当てていません。

### ゲートが捕まえられないもの（重要）

**係り受けの誤り**は、どのゲートでも検出できません。固有名詞は実在し、語彙は現代語で、字数も範囲内、しかし主語が違う——という誤りです（試作でごん狐の主語を取り違えた実例あり）。

**これを捕まえられるのは人の目だけです。** だから第8章の人手検品が要ります。

## 6. 確定している設計判断

### 6-1. 生成対象は 16,203件

```
全作品                17,456件
− 本文200字未満          895件（案内文が原文より長くなるため）
− 表記違いの統合         358件（下記）
= 生成対象           16,203件
```

**表記違いの統合について：** 案内文は「今日の言葉」で書くので、本文の文字遣いに依存しません。羅生門の新字新仮名版（ID 127）と旧字旧仮名版（ID 128）は**同じ案内文を共有できます**。同一著者・同一題名・文字数±10%以内・文字遣いが互いに異なる352組を統合し、358件の生成を省きます。

**ただし `index.json` のエントリは統合しません。** 共有するのは案内文とラベルだけ。はじまりの一文は各版の原文のままです（表記が違うので）。

文字遣いまで同じ23組は**統合しません**。別作品の可能性があり、誤って同一視すれば事実の誤りになるからです。

### 6-2. 入力は本文の先頭4,000字のみ

**結末を見せないための構造的な対策**です。指示で「結末に触れるな」と言うのではなく、そもそも結末を渡しません。

第1便で有効性が実証されました。舞姫では**冒頭4,000字にエリスが登場しない**ため、案内文からエリスが自然に消えました。一般教養（舞姫といえば悲恋）による汚染も同時に防げています。

### 6-3. 案内文の型は2つある

| 対象 | 型 |
|---|---|
| 物語 | 誰が・どこで・何をする話か |
| 随筆・評論 | 何を手がかりに・何について、どう論じているか |

第1便の最大の発見です。随筆22篇中21篇（95.5%）に案内文を書けました。**「随筆には案内文が書けない」は誤りでしたが、小説の型をそのまま当てはめるのも誤りです。**

### 6-4. 「育つ庭」モデル

**全16,203件の案内文が揃うことは、公開の条件ではありません。**

第一段階の成果だけで「15分で読める口語の短編」検索（10,670件）は既に成立しています。案内文は土台ではなく、上に載る改善です。

生成順序は**青空文庫の公式アクセスランキング順**（読まれる作品から先に）。ただしUI側に規律を課します：

1. 案内文の有無で並べ替えない
2. 「案内文準備中」等のラベルを出さない
3. 案内文がない作品も同じ視覚的重みで表示する（はじまりの一文がその場所を満たす）

**不在を欠落として見せない。** これが守られる限り、人気順生成は序列を生みません。

| 軸 | 4,000字での実績 | 2,000字での合格線 |

### Day 2：リポジトリ戦略

**2-1. 軽量版リポジトリの調査（先にやること）**

`aozorabunko/aozorabunko_text` という軽量リポジトリが存在するようですが、**第一段階から未検証のまま宿題として残っています**。本文XHTMLが揃っているか、更新は追随しているかを実際に確認してください。

使えるならディスクを大幅に節約できます。**使えるかどうかを自分で確かめてから採否を決めること。**

**2-2. クローン**

軽量版が使えないなら本家 `aozorabunko/aozorabunko` を：

- `--depth 1`
- **`--filter=blob:none` のままにしないこと**（4-1参照）

ディスクは数GB〜十数GBを見込んでください。**実測して報告すること。**

### Day 3〜4：ベンチマーク（第3便の中心的な検査）

**手書き97篇（`drafts_batch1.json`）を対照群として使います。** これは会話の中で1件ずつ本文を読んで書いたもので、この工程で到達しうる品質の上限に近いものです。

| 項目 | 合格線 |
|---|---|
| 第三層（固有名詞）最終通過率 | 95%以上 |
| 手書き版との固有名詞一致率 | Jaccard 0.6以上 |
| 字数規格（60〜100字） | 100% |

## 8. 本番運用（較正が終わってから）

### 8-1. 毎日の型

運営者がやることは `claude` を起動して「続き」と打つだけです。あなたがやること：

1. `/status` で認証確認
2. `state/checkpoint.jsonl` を読み、優先順リストの未処理IDを取得
3. N件ずつ処理：
   - 本文の先頭4,000字を読む（**それ以上読まない**）
   - 案内文と4軸ラベルをJSONで書く
   - `gates.py` にかける
   - 不合格なら修正。**上限3回**。3回落ちたら `案内文なし理由: "ゲート不合格（3回）"` として確定させ、次へ進む
4. **1件ごとに** checkpoint へ追記（途中で止まっても失われないように）
5. 枠が尽きそうになったら、進捗サマリ（済/残/推定完了日）を出して終了

### 8-2. 出力形式

```json
{
  "作品ID": "127",
  "案内文": "夜、羅生門の下で雨宿りする男。...",
  "案内文なし理由": null,
  "形式": ["小説"],
  "主題": ["貧困", "死", "身分・階級"],
  "読後感": ["不穏", "張りつめた"],
  "時代の質感": ["平安"]
}
```

**`案内文なし理由` を必ず使えるようにしておくこと。** 書けないときに書かせない逃げ道がないと、必ず何かを書いてしまいます。それが嘘の温床です。

### 8-3. 人手検品（第六層）— これは運営者の仕事

生成と並行して、運営者が**層化抽出で200〜400件**を読み、案内文が本文に照らして正しいかを判定します。

- 判定は**はい／いいえ／判断保留**の三択のみ。それ以上求めないこと（重くすると終わらない）
- 厚く見る層：随筆・評論／文語・旧字旧仮名／長大な作品／**ゲートを2回以上落ちて通った作品（全件）**
- 薄くてよい層：短い口語小説

**係り受けの誤りを捕まえられるのは人の目だけです。** ここを省くと、16,203件の誤り率が永久に不明のまま公開されます。

あなたの役割は、検品しやすい形（作品ID・案内文・本文冒頭を並べた一覧）を用意することです。

## 10. 最後に

このプロジェクトが第一段階から一貫して守ってきたのは、**検証していないことを検証済みと言わない**という一点です。

実際、これまでの各段階で見つかった欠陥は、すべて「動いているように見えたが、都合のよい条件下でだけ動いていた」ものでした。文語判定を1作品に合わせて検証済みとした件。文末の偏りを見えなくする集計をしていた件。生成側が正直に申告した場合にだけ機能するゲートを、機能するゲートとして報告した件。

**破れなかったという報告より、破れ方を見つけた報告のほうが価値があります。** ゲートが破れる条件を、自分から探しにいってください。

そして急がないでください。青空文庫は30年かけて17,456件を積みました。その隣に立つものが、2か月を惜しむ理由はありません。
