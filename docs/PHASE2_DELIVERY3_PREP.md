## 第一部：検証結果

### 1-1. 核心の主張は、公式ソースで裏が取れた

Fableの計画は「Claude Codeは購読料に含まれ、追加費用ゼロ」という一本の柱に乗っている。ここが崩れると全部崩れるので、公式情報で確認した。

**確認できたこと**（出典：Anthropic公式）：

> Claude Code is included in all paid plans. It shares the same usage limits as the rest of your plan, so your work in the terminal and your chats draw from one pool.
> — https://claude.com/pricing

> Both Pro and Max plans offer usage limits that are shared across Claude and Claude Code, meaning all activity in both tools counts against the same usage limits.
> — https://support.claude.com/en/articles/11145838-use-claude-code-with-your-pro-or-max-plan

**Fableの主張は正しい。** 有料プランならClaude Codeは追加課金なしで使え、利用枠はチャットと共有される。

---

### 1-2. 【最重要】踏みかねない罠が一つある

公式サポート記事に、この計画にとって決定的な注意書きがある。

> **Important:** If you have an `ANTHROPIC_API_KEY` environment variable set on your system, Claude Code will use this API key for authentication **instead of your Claude subscription**, resulting in **API usage charges** rather than using your subscription's included usage.
> — 同上（support.claude.com）

つまり：

> **`ANTHROPIC_API_KEY` が環境変数に設定されていると、Claude Codeは購読を無視してAPI課金に切り替わる。**

これは他人事ではない。**この会話で我々は直前までAPIキーの話をしていた。** もし運営者が「APIキーが要るのか」と考えて先に設定してしまっていたら、ゼロ円のつもりで数百ドルの請求が発生する。16,203件を回した後に気づくのが最悪のパターンである。

**対処（実行前に必ず確認すること）：**

```bash
# macOS / Linux / WSL
echo $ANTHROPIC_API_KEY
#   → 何も表示されなければOK
#   → 何か表示されたら、下記で解除する
unset ANTHROPIC_API_KEY
```

```powershell
# Windows PowerShell
echo $env:ANTHROPIC_API_KEY
#   → 空ならOK。値があれば下記で解除
Remove-Item Env:\ANTHROPIC_API_KEY
```

`.bashrc` `.zshrc` `.zprofile` などに `export ANTHROPIC_API_KEY=...` が書かれていないかも確認すること。書いてあれば、その行を消すかコメントアウトする。

**そして、Claude Code起動後に必ず `/status` を実行し、認証がサブスクリプション側になっていることを目視で確認する。** これを第1週の較正の最初のチェック項目とする。

---

### 1-3. もう一つの前提：無料プランでは使えない

公式は「Claude Code is included in **all paid plans**」と書いている。裏を返せば**無料プランは対象外**である。

したがって：

- 運営者が現在**無料プラン**なら → Pro（月$20、年払いなら月$17相当）への加入が必要
- **これがこのプロジェクトの事実上の全予算になる。** 2〜3か月で$40〜60程度
- Pro以上にすでに加入済みなら → **追加費用は本当にゼロ**

**最初にやること：現在のプランを確認する**（claude.ai → 設定 → プラン）。ここが分からないと計画の費用が確定しない。

---

### 1-4. Fableが触れなかった、正直に見ておくべき副作用

**利用枠はチャットと共有される。** これは公式に明記されている。つまり：

> 生成を回した日は、Claude とのチャットに使える枠が減る。

一人で運用する以上、この共食いは避けられない。「今日は生成の日」「今日は相談の日」と分ける運用が現実的である。第4便以降の設計相談をしたい日は、生成を止めればよい。**急ぐプロジェクトではないので、これは許容できる。**

## 第二部：七つの判断（Fableの9章への回答）

### 判断1：三つの手すべてを採用する

| 手 | 裁定 | 条件 |
|---|---|---|
| 手1：育つ庭（完成の定義を変える） | **採用** | 判断2の規律とセット |
| 手2：Claude Codeを生成エンジンにする | **採用** | 1-2節のAPIキー確認を必須の前提とする |
| 手3：表記違い358件の統合 | **採用** | 判断4の但し書きつき |

手1については補足する。これは技術判断ではなくプロダクト哲学の判断であり、私が採用する根拠は外部にない——**元のPHASE2_SPEC.md自身が「案内文を作らず、はじまりの一文と計測値だけで出す」を正当な選択肢として明記している**。Fableはそれを見つけて持ってきた。設計書に既に書かれていたものを実行するのは、方針転換ではなく方針の遂行である。

---

### 判断2：人気順生成と「序列をつけない」原則の裁定

**Fableが指摘した緊張は本物である。** 生成順序自体は作業の都合であり、UIに漏れなければ問題ない。しかし案内文が付いた作品と付いていない作品が混在する期間、前者が「格上」に見えるという懸念は、実際に起こりうる。

**裁定：生成順序は人気順を採用する。ただしUI側に以下の規律を課す。**

1. **案内文の有無で並べ替えない。** 検索結果の順序に案内文の有無を一切反映させない
2. **「案内文準備中」等のラベルを出さない。** 欠けているのではなく、**そこには はじまりの一文がある**という表示にする
3. **案内文がない作品も、ある作品と同じ視覚的重みで表示する。** 枠を空けて待つのではなく、はじまりの一文がその場所を満たす

つまり**不在を欠落として見せない**。これが守られる限り、人気順生成は序列を生まない。

**この3点を第三段階（UI設計）への申し送りとして確定させる。** 育つ庭という考え方が原則と両立するかは、UIの規律次第である。

### 判断3：Pass A/B分離 —— 検証を先に行う

**2,000字への短縮検証は実施する。** 既存の100篇データで完結し、費用ゼロ、Claude Code導入前に今すぐ着手できる。

**合格基準を先に決めておく**（結果を見てから基準を決めるのは、第1便で戒めたやり方である）：

| 軸 | 4,000字での実績 | 2,000字での合格線 |
|---|---|---|
| 形式 | 0.950 | **0.90以上** |
| 主題 | 0.720 | **0.65以上** |
| 読後感 | 0.682 | **0.60以上** |
| 時代の質感 | 1.000 | **0.90以上** |

全軸が合格線を満たせばPass A（ラベル先行・全件）を採用。一つでも下回れば分離せず、案内文とラベルを同時に生成する。

### 判断4：358件統合を採用。要注意23組は統合しない

**352組・358件の削減を採用する。** 根拠が明快だからである——案内文は今日の言葉で書くので、本文の文字遣いに依存しない。原則から自然に導かれた実利であり、こじつけではない。

**ただし要注意23組（文字遣いまで同一の組）は統合しない。**

理由：23件は16,203件に対して0.14%である。**取りこぼしても誤差だが、別作品を誤って同一視すれば、それは事実の誤りになる。** 天秤は明らかに片側に傾いている。判定ロジックを設計する労力も、23件を素直に生成する労力を上回る。

これは第一段階以来の規律——**疑わしいものは統合せず、別として扱う**——の踏襲である。

**確定：生成対象 16,203件。**

### 判断5：ベンチマークの設計

**N ∈ {3, 8, 15} で97篇ベンチマークを実施する。** 合格基準を先に定める：

| 項目 | 合格線 | 根拠 |
|---|---|---|
| 第三層（固有名詞）最終通過率 | **95%以上** | 手書き版は100%。多少の劣化は許容 |
| 手書き版との固有名詞一致率 | **Jaccard 0.6以上** | 同じ作品を読めば同じ固有名詞に触れるはず |
| 字数規格（60〜100字） | **100%** | 機械的に守れるはずの項目 |
| 型の選択（小説型/随筆型）の一致 | **90%以上** | 第1便の最大の発見を再現できるか |
| 文末の偏り（形式名詞軸・用言軸） | **各20%未満** | 第1便の差し戻し基準を維持 |

**全項目を満たす最大のNを本番値とする。** 満たすNが一つもなければ、プロンプトを直してやり直す。Nを下げれば必ず良くなるとは限らないので、N=3でも駄目ならプロンプト側の問題である。

## 第三部：Claude Code の使い方（はじめての方向け）

### 3-1. Claude Code とは何か

一言でいうと、**あなたのパソコンの中で動くClaude**です。

いま使っているclaude.aiのチャットとの違いは、こうです。

| | claude.ai（今使っているもの） | Claude Code |
|---|---|---|
| 場所 | ブラウザの中 | あなたのパソコンの中 |
| ファイル | 都度アップロードが必要 | **パソコン上のファイルを直接読み書きできる** |
| 記憶 | 会話が続く限り覚えている（長くなると重くなる） | **毎回まっさらに始まる。記憶はファイルに書く** |
| 料金 | 購読に含まれる | **同じ購読に含まれる（追加費用なし）** |

雲間にとって決定的なのは3行目です。会話方式が破綻するのは記憶が累積するからでした。Claude Codeは毎回白紙で始まり、「どこまで終わったか」を**ファイルから読みます**。これがあなたの言った「チェックポイントファイルを作れば重複はなくなる」という発想が、本来あるべき場所です。

**「コード」という名前ですが、プログラミングをする必要はありません。** あなたがやるのは、日本語で指示を出すことだけです。

---

### 3-2. 準備するもの

1. **有料プラン**（Pro以上）——無料プランでは使えません
2. **ターミナル**——パソコンに最初から入っている、文字を打ち込む黒い画面
   - Mac：「ターミナル」（アプリケーション → ユーティリティ の中）
   - Windows：「PowerShell」（スタートメニューで検索）
3. **ディスクの空き**——青空文庫のリポジトリを置くため。**要実測ですが、数GB〜十数GBを見込んでください**

### 3-3. 導入手順

**手順は変わることがあるので、必ず公式ページを最初に開いてください：**
https://code.claude.com/docs/en/quickstart

以下は2026年7月時点の内容です。

**ステップ1：APIキーの確認（最重要・飛ばさないこと）**

インストール前に、1-2節の確認を行ってください。ここを飛ばすと課金されます。

```bash
# Mac / Linux
echo $ANTHROPIC_API_KEY
```
```powershell
# Windows
echo $env:ANTHROPIC_API_KEY
```

**何も表示されなければOK。** 何か出たら解除してください（1-2節参照）。

**ステップ2：インストール**

2026年現在は「ネイティブインストーラ」が推奨されています。

```bash
# Mac / Linux / WSL
curl -fsSL https://claude.ai/install.sh | bash
```
```powershell
# Windows PowerShell
irm https://claude.ai/install.ps1 | iex
```

終わったら、**ターミナルを一度閉じて開き直して**から確認します。

```bash
claude --version
```

バージョン番号が出れば成功です。`command not found` と出る場合は、公式のトラブルシューティングを見てください。

**ステップ3：起動とログイン**

作業したいフォルダに移動してから起動します。

```bash
cd ~/kumoma        # 雲間用のフォルダ（後で作ります）
claude
```

初回はブラウザが開いてログインを求められます。**claude.aiで使っているのと同じアカウントでログインしてください。** これで購読と紐づきます。

**ステップ4：認証の確認（必須）**

起動したら、まずこれを打ってください。

```
/status
```

**サブスクリプション（Pro/Max）で認証されていることを目視で確認します。** APIキー経由になっていたら、いったん終了してステップ1に戻ってください。

### 3-4. 基本の使い方

起動すると `>` という入力待ちの状態になります。ここに**日本語で指示を書くだけ**です。

```
> index.json を読んで、作品数を教えて
```

Claude Codeはファイルを読み、答えます。ファイルを変更するときは「こう変更していいですか」と許可を求めてくるので、確認して許可します。

**覚えておくと便利なコマンド：**

| コマンド | 意味 |
|---|---|
| `/status` | 認証状態の確認（**毎回最初に**） |
| `/usage` | 利用枠がどれくらい残っているか |
| `/clear` | 会話をリセットして軽くする |
| `exit` | 終了 |

**利用枠の仕組み：** 5時間ごとに回復する枠と、週ごとの上限の2段構えです。枠を使い切ったら、その日はそこで終わり。**これが自然な日次の区切りになります。**「今日はここまで」を機械が決めてくれるので、無理な連続作業になりません。

---

### 3-5. 毎日の作業（本番が始まったら）

あなたが毎日やることは、実質これだけです。

```bash
cd ~/kumoma
claude
```

そして：

```
> 続き
```

これだけ。Claude Codeがチェックポイントを読み、続きから処理し、枠が尽きたら進捗を報告して止まります。

### 3-6. `CLAUDE.md` 草案（判断7）

`CLAUDE.md` は、**Claude Codeが毎回自動で読む指示書**です。これをリポジトリに置いておけば、毎回説明し直す必要がありません。まさに「リポジトリと共に旅する仕様書」です。

以下を `~/kumoma/CLAUDE.md` として保存してください（本番開始前に最終確定します）。

```markdown
# 雲間 — 案内文・ラベル生成プロジェクト

## このプロジェクトについて
青空文庫の全作品に「案内文」（60〜100字）と4軸ラベルを付ける。
生成対象は 16,203件。急がない。正確さが速さに優先する。

## 「続き」と言われたら
1. state/checkpoint.jsonl を読み、未処理の作品IDを優先順リストから取得
2. N件ずつ処理する（Nは calibration.md の確定値に従う）
   - 本文の先頭4,000字のみを読む（それ以上読まない。結末を見ないため）
   - 案内文とラベルをJSONで書く
   - gates.py にかける
   - 不合格なら修正。**上限3回**。3回落ちたら
     「案内文なし理由: ゲート不合格（3回）」として確定させ、次へ進む
3. **1件ごとに** checkpoint.jsonl へ追記する（途中で止まっても失われないように）
4. 利用枠が尽きそうになったら、進捗サマリ（済/残/推定完了日）を出して終了

## 案内文の規格
- 60〜100字。事実主軸。**結末に触れない**
- **今日の言葉で書く。** 本文の語彙をそのまま流用しない
  （NG例：廓・楼上・麦酒・従僕・逢引）
- **固有名詞は本文の表記のまま。** 旧字体・当て字を現代表記に直さない
  （豐太郎を豊太郎にしない／亜米利加をアメリカにしない）
- **本文に書かれていないことを具体化しない**
  （本文が「わが國」なら「日本」と書き換えない）
- 評価語（傑作・名作・代表作など）を使わない
- 文末を「〜随筆。」「〜評論。」で終えない。形式は形式ラベルが担う

## 型の選び分け
- 物語 → 「誰が・どこで・何をする話か」
- 随筆・評論 → 「何を手がかりに・何について、どう論じているか」

## ラベル
label_vocab.py の閉じた語彙からのみ選ぶ。自由記述は禁止。1軸あたり最大3つ。

## 絶対にやらないこと
- **本文200字未満の作品に案内文を付けない**（under200_ids.json 参照）
- 既存の計測値・はじまりの一文を変更しない（第一段階の成果物）
- ゲートの誤検知を消すために語彙リストへ語を追加しない
- 書けないものを無理に書かない。**「案内文なし理由」を必ず使えるようにしておく**

## 迷ったら
書かない。空欄は誤りより良い。
```

## 第五部：最後に

Fableの設計書の背骨は、**あなたの案が正しかった**という一点にあります。チェックポイントを作って地道に数か月——これは捨てられていません。置き場所が変わっただけです。

そして今回の検証で、その計画に一つだけ地雷があることが分かりました。`ANTHROPIC_API_KEY` です。皮肉なことに、我々がこの会話でAPIキーの話をしたせいで、あなたが親切心から先に設定してしまう可能性が最も高い状態にあります。**準備リストの2番を、他の何より先にやってください。**

急ぐ必要はありません。青空文庫は30年かけて17,456件を積みました。準備に一日かける程度のことは、このプロジェクトの時間感覚では一瞬です。
