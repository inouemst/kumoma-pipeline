## 1. 【最優先】第1段階で見つかった検証機構の欠陥 — 必ず先に直すこと

### 1-1. 何が起きていたか

第1段階の「著者名漏出チェック」は、`stage1_meta.json` の `著者名` フィールドに依存していた。
しかし **169件中20件で、この `著者名` が空文字だった。**
空文字は「照合すべき名前がない」として扱われ、**チェックが素通りしていた。**

原因は2つ：

| パターン | 件数 | `batchN_meta.json` の `著者ID` | 実際の著者 |
|---|---|---|---|
| 著者IDが空 | 9件 | `''` | `index.json` の `著者` 欄には入っている（芥川竜之介、宮沢賢治、梶井基次郎 等） |
| 共著の複合ID | 11件 | `'96、966'` `'1091、1092'` 等 | `authors.json` は単一ID索引のため引けない |

**幸い、第1段階の20件を事後に再照合した結果、実際の漏出は0件だった**（公開済みデータに問題はない）。
だが**チェック機構が信頼できない状態だった**という事実は残る。

### 1-2. どう直すか

**`batchN_meta.json` の `著者ID`→`authors.json` という経路をやめ、
`index.json` の `著者` 欄を直接使うこと。** ここには共著も含めて著者名が文字列で入っている。

```python
index = json.load(open("index.json", encoding="utf-8"))
idx_by_id = {w["作品ID"]: w for w in index["作品"]}
# 著者名の取得
au_string = idx_by_id.get(wid, {}).get("著者") or ""
# 例: "夢野 久作、海若 藍平　→" / "グリム ヤーコプ・ルートヴィッヒ・カール、グリム ヴィルヘルム・カール"
```

照合時は次のように分解する（第1段階の事後検証で実際に使い、正しく動作したロジック）：

```python
import re
names = set()
for part in re.split(r"[、,]", au_string):
    part = part.replace("→", "").strip()
    if not part:
        continue
    names.add(part.replace(" ", "").replace("　", ""))   # 姓名を詰めた形
    for tok in re.split(r"[ 　]+", part):                 # 姓・名それぞれ
        if len(tok) >= 2:
            names.add(tok)
# names のいずれかが案内文に含まれていれば漏出の疑い
```

**`prepare_stage2_fix.py`（作成する）では、`stage2_meta.json` の `著者名` に
必ず `index.json` 由来の文字列を入れること。** 空にしてはならない。
空になる作品が1件でもあれば、そこで止めて報告すること。

### 1-3. 共著作品では「もう一方の筆名」も漏出対象

第1段階に含まれていた夢野久作の共著作品群（`96、966` 等）で、
`海若 藍平` `香倶土 三鳥` `萠円` などは **いずれも夢野久作自身の別筆名**である。
`CLAUDE.md` 4章の「著者の雅号・筆名も書かない」に該当するので、
共著欄に並ぶ名前は**全て**照合対象に含めること（上記ロジックはこれを満たす）。

## 4. 字数について（第1段階の反省を踏まえた指示）

### 4-1. 第1段階で起きたこと

目安「63〜75字」と指示したにもかかわらず、実際の分布は次のとおりだった。

| 字数帯 | 件数 |
|---|---|
| 60〜70字 | 7件 |
| 71〜80字 | 8件 |
| 81〜90字 | 17件 |
| **91〜100字** | **137件（81%）** |

規格（60〜100字）は守られており実害はないと運営者が判断し、そのまま採用した。
だが**「短い作品ほど圧縮しすぎない」という当初の趣旨とは逆方向**であり、
第2段階では改善を試みる。

### 4-2. 第2段階での指示

エージェントへのプロンプトに、次を**明示的に**含めること。

> **字数は60〜100字。ただし75字を超えたら一度立ち止まり、
> 「この情報は読む動機を作るために本当に必要か」を自問し、削れるなら削ること。
> 上限100字は「守るべき天井」であって「目指すべき目標」ではない。**

### 4-3. 検証時の扱い

生成後、**字数分布を必ず集計して報告に含めること**（第1段階では事後に判明した）。
85字超の件数が全体の5割を超える場合は、マージ前に運営者へ報告し判断を仰ぐこと。
**勝手に再生成をかけない**（コストがかかるため）。

## 5. 作業手順

### 5-1. 準備スクリプト `prepare_stage2_fix.py` を作る

`prepare_stage1_fix.py` を基に、以下を変更して作成する。

- 抽出条件：物語系（小説/童話/戯曲/脚本）**かつ 0.6 ≤ 露出率 < 0.9**
- **著者名は `index.json` の `著者` 欄から取る**（1-2節。ここが最重要の変更点）
- 出力：`stage2_meta.json` / `stage2_input.json` / `stage2_fulltext_full.json` / `stage2_old_guide.json`
- 実行後、**著者名が空の作品が0件であることを確認**してから次へ進む

### 5-2. 検証ツール `gate_check_stage2.py` を作る

`gate_check_stage1.py` の参照先を `stage2_fulltext_full.json` に変えるだけ。

### 5-3. エージェントに生成を依頼

第1段階のプロンプトを基に、以下を反映する。

- **B型の説明は削る**（第2段階には該当なし）
- 4-2節の字数指示を明記
- 3章の同名異作4組を注意事項として明記
- 芥川30件の集中と、自作・自身への言及に関する注意
- 出力は `stage2_corrections.json`、形式は第1段階と同じ（`案内文`/`判定`/`型`）
- **分割は3グループまで、最終検証は1ファイルにまとめて1回だけ**（第17バッチの
  権限プロンプト急増の反省。`GUIDE_TEXT_SPEC_V2.md`にはないが運用上の必須事項）
- `state/checkpoint.jsonl` `CLAUDE.md` `production_batchN.json` `kumoma_prototype.html` を
  触らせない／git操作をさせない

### 5-4. 独立検証（自己申告を信用しない）

エージェントの報告を鵜呑みにせず、呼び出し側で次を実施する。

1. `python gate_check_stage2.py --all stage2_corrections.json` を自分で実行
2. **著者名漏出チェックを 1-2節のロジックで独立に実施**（`index.json` 由来の著者名を使う）
3. 字数分布の集計（4-3節）
4. 143件全件のエントリがあることの確認

### 5-5. レビューページへの反映

`build_retro_review.py` の `load_corrections()` は現在 `stage1_corrections.json` のみを
読んでいる。**`stage2_corrections.json` も併せて読み込むよう拡張すること**
（両方をマージした辞書を返す）。バッジ表示やフィルタのロジックは変更不要。

生成後、`review_retro.html` を `kumoma-site` の `review-retro.html` にコピーして公開し、
運営者が第2段階分を確認できる状態にする。

### 5-6. マージ（運営者の承認後のみ）

**承認を得るまでマージしないこと。** 承認後は `apply_stage1_corrections.py` を基に
`apply_stage2_corrections.py` を作り、`由来` を `revision_stage2` として
`checkpoint.jsonl` に追記＋`kumoma_prototype.html` の `D` 配列を更新する。
