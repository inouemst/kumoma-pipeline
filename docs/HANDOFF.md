# 引き継ぎ資料 — 雲間プロジェクト

> 新しいチャットへの移行用。ここまでの決定事項と現在地。

---

## プロジェクト概要

**雲間（くもま）** — 青空文庫への入口となる、非営利の静的サイト。

青空文庫には約17,000作品があるが、実際に読まれているのはごく一部。アクセスは完全に自由なのに、出会いだけが起きていない。この一点だけを解決する。

**読む機能は持たない。読者は青空文庫へ送り返す。**

---

## なぜこの空白が存在するのか（調査済み）

1. **青空文庫は「保存する図書館」として設計されており、「出会わせる場所」ではない。** 底本に忠実であることが規律であり、要約や恣意的な分類を加えないのは正しい判断。
2. **あらすじが無いのは、ほぼ著作権が理由。** 文庫本のカバーあらすじや解説は編集者が書いた別個の著作物であり、本文の著作権が切れていてもそれらは切れていない。
3. **既存の青空文庫アプリ（ソラリ、i文庫S、Yom!青空文庫 等）は「読む体験」の最適化に集中しており、発見機能は新着順とアクセスランキング止まり。**
4. **一般書籍向けのAI選書サービスは既に存在するが、対象はAmazon等の有料書籍で、青空文庫には繋がっていない。**

→ ①青空文庫特化だが探せない ②探せるが青空文庫と繋がっていない、の間に空白がある。

---

## 五つの原則

1. **寄生しない** — 青空文庫の顔を奪わない
2. **上書きしない** — 本文には触れない
3. **序列をつけない** — 人気ランキングは作らない。既知度の低い作品を優先的に照らす
4. **利益を目的にしない** — 広告・課金なし
5. **いつでも消えられるようにしておく** — 生成データはオープンライセンスで公開

---

## 固まっている設計判断

### アーキテクチャ

- **完全静的・サーバーなし。** 埋め込みを256次元int8に量子化すれば全17,000作品で約4.4MB。ブラウザに丸ごと配れる
- 検索は端末内で完結 → 検索ログが原理的に取れない、どこでもホストできる、オフラインでも動く
- 実行時にAIを呼ばない。すべて事前生成のバッチ処理
- 更新は月次の差分バッチ（新規収録は年間数百件程度）

### 五つの入口

1. **言葉から** — 意味検索（「働くのに疲れた」等）
2. **時間から** — 読了時間で絞る（**最も過小評価されている軸**）
3. **読みやすさから** — 文語/口語、旧仮名、漢字率
4. **偶然から** — 日替わり／無作為。既知度の低い作品ほど出やすく重み付け
5. **隣から** — ベクトル空間の近傍探索

### 案内文の設計（試作で確定）

**役割分担が核心：**

| | 担うもの | 言葉づかい |
|---|---|---|
| **はじまりの一文** | 作品の声 | 原文のまま、一字も変えない（機械抽出・検証不要） |
| **案内文** | 読者への案内 | **今日の言葉に置き換える** |

- 60〜100字、事実主軸（誰が・どこで・何をする話か）、結末に触れない
- 読後感・評価はラベル側に寄せる
- **固有名詞は本文準拠。置き換えるのは説明のための一般語彙だけ**
- 既存の解説やWikipediaは参照しない

### クレジット表示

入力者・校正者・底本を**雲間の作品ページ自身に表示する**。リンク先（図書カード／本文）は読者に選ばせる。敬意は他所へ送ることではなく、自分の画面に名前を出すことで果たす。

## 品質保証の六層

最大のリスクは17,000件の事実誤認。最大の制約は運営者が全作品を読めないこと。人力ではなくパイプラインの構造で担保する。

1. **引用は決して間違えない** — はじまりの一文は機械抽出
2. **機械で取れる事実は機械で取る** — 固有名詞・地名・計測値
3. **自動照合で機械的に弾く** — 案内文の固有名詞が本文に実在するか
4. **言葉の壁を案内文自身が作らない** — 非流通語を機械的に弾くゲート
5. **誤りの上限を設計で下げる** — 結末に触れない、100字、事実主軸
6. **人の目は、見られたものにだけ注ぐ** — 抜き取り＋GitHub Issueでの報告導線

---

## 試作の結果（完了済み）

実データで8篇の案内文を試作し、全篇が自動検品を通過。

**得られた知見：**

- **記憶とテキストが食い違う実例が出た。** たけくらべに「吉原」を使おうとしたが本文に一度も登場せず、実際は「大音寺前」だった
- **テンプレ化が初稿で実際に起きた。** 8篇中4篇が「〜ていく。」で終わっていた
- **案内文が作品の語彙に引きずられた。** 「廓」「楼上」「麦酒」「従僕」「逢引」が混入 → 現代語ゲートを実装して解決
- **現代語化は読みやすさだけでなく事実の精度も上げた。** 「逢引き」→「別れぎわのやりとり」の方が場面として正確だった
- **係り受けの誤りは機械では捕まらない。** ごん狐で主語の取り違えが発生。第六層が必要な理由

## 検証済みの技術情報

- リポジトリ：`aozorabunko/aozorabunko`（GitHub APIはレート制限で使えない。git cloneを使う）
- `index_pages/person{N}.html` — **整数表記**（person42 であって person000042 ではない）
- `cards/{人物ID6桁}/files/{作品ID}_{ファイルID}.html` が本文XHTML
- 文字コードは **Shift_JIS**
- 本文は `<div class="main_text">`
- クレジットは `<div class="bibliographical_information">`（**bibliography_information ではない**）
- ルビは `<ruby><rb>漢字</rb><rp>（</rp><rt>かんじ</rt><rp>）</rp></ruby>`
- **文字遣い（新字新仮名等）は青空文庫の公式メタデータ。** person ページから読み取れるので推測不要
- 同一作品に複数バージョンが存在する（羅生門＝127と128）
- 翻訳作品は著者側・訳者側の双方のpersonページに現れる → 作品IDで重複排除が必要
