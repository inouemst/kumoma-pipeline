# 第3便・打開策設計書 — 会話の壁を越える三つの手

> 雲間 / Phase 2。Fableによる横断レビューと打開提案。次のOpusはこれを検証し、採否を決め、第3便仕様書を改訂すること。
> 前提：**このプロジェクトは無収益であり、費用を極力かけない。** 運営者は1〜3か月の地道な作業を厭わない。

---

## 0. 結論の要約

第3便は「APIに数百ドル払うか、会話で10か月かけるか」の二択で止まっている。**この二択は偽物である。** 壁の正体はお金ではなく、「一つの会話にすべてを載せようとしていること」にある。

三つの手で崩す：

1. **完成の定義を変える** — 全16,561件の案内文はローンチ条件ではない。元の設計自身がそれを認めている
2. **生成エンジンを会話からClaude Codeへ移す** — 運営者がすでに払っている定額の枠内で回る。追加費用ゼロ
3. **対象を圧縮する** — 表記違いバージョンの統合で358件削減（この場で実測済み）

運営者自身が出した「チェックポイントファイル＋数か月の地道な継続」という案は、**正しかった**。ただし置き場所が違った。一つの会話は過去の文脈を毎ターン背負い直すため長期反復に耐えないが、Claude Codeは**毎セッション白紙で始まり、記憶をファイルから読む**。チェックポイント方式が設計通りに機能するのは、そちらの環境である。

## 1. 壁の正体の再診断

Sonnetの試算（966ターン、4〜10か月）は正しい。しかしその試算が示しているのは「会話が向いていない」ことであって、「定額の枠内では不可能」ということではない。

会話ベースが破綻する本当の理由：

- **文脈の累積**。1件処理するたびに会話が伸び、次の1件のコストが上がる。16,000件分の履歴は物理的に文脈に収まらない
- **状態の脆さ**。セッションが切れたら「どこまでやったか」を人が思い出して伝え直す必要がある

Claude Codeはこの二つを構造的に持たない：

- 毎セッションが白紙。処理済みIDは `checkpoint.jsonl` から読む（第一段階で実証済みの方式そのまま）
- 定型の指示は `CLAUDE.md` に書いておけば毎回自動で読まれる。**仕様書がリポジトリと一緒に旅をする**
- Pro以上のプランなら、Claude Codeの利用は購読料に含まれ、トークン従量課金がない（2026年6月15日の課金変更で明確化。利用枠はclaude.aiチャットと共有）

つまり運営者が今この会話に使っているのと**同じ購読**で、生成エンジンが手に入る。追加費用はゼロ。

## 2. 手1：完成の定義を変える

### 2-1. 根拠は元の設計書の中にある

PHASE2_SPEC.md 3-1節：

> それとも案内文を作らず、はじまりの一文と計測値だけで出すか（**これも正当な選択肢**）

第一段階の成果がすでに証明していること：「15分で読める口語の短編」検索（10,670件ヒット）は、**LLM生成物を一つも使わずに**成立する。案内文は雲間の土台ではなく、上に載る改善である。

### 2-2. 「育つ庭」モデル

- **ローンチ時点**：全作品が検索可能（計測値＋はじまりの一文＋ラベル）。案内文は付いている作品から順次表示
- **以後**：案内文のカバレッジが毎日少しずつ広がる。これは欠陥ではなく、青空文庫自身が30年かけて作品を増やしてきたのと同じ**運動の形**である

### 2-3. 生成の優先順位：読まれる順に

青空文庫は公式にアクセスランキング（上位500位、XHTML版）を公開している（検証済み：https://www.aozora.gr.jp/access_ranking/ 。最終更新2023年1月、**2022年通年が最新**）。

これを優先順位に使う。年間上位500件に最初の1〜2週間で案内文が付けば、**実際に読まれる作品の大半が早期にカバーされる**（2021年の外部分析では、上位500位のアクセス総数の約7割を上位10著者が占める——読者到達は極端にロングテールである）。

**正直に記す制約**：ランキングは2022年で更新停止している。ただし百年前の古典の読まれ方は年単位では大きく動かないため、優先順位付けの用途には耐えると判断する。複数年（2018〜2022）の和集合を取れば頑健性も上がる。

**原則との緊張を一つ申告する**：「序列をつけない」原則に対し、人気順の生成順序は緊張を持つ。これは**作業の順序であって、UI上の序列ではない**という整理が可能だが、案内文が付いた作品と付いていない作品が混在する期間、前者が「格上」に見える懸念は残る。Opusはこの緊張を検討し、UI側の扱い（第三段階への申し送り）を決めること。

## 3. 手2：Claude Codeを生成エンジンにする

### 3-1. 仕組み

APIを呼ぶスクリプトを書くのでは**ない**。Claude Code自身が読み、書く。エージェント自体が生成器である。

毎日のセッションの型（`CLAUDE.md` に記載しておく）：

```
1. checkpoint.jsonl を読み、優先順リストの未処理IDを取得
2. N件ずつ処理：本文先頭4,000字を読む → 案内文＋4軸ラベルをJSONで書く
   → gates.py にかける → 不合格なら修正（上限3回）→ 結果を追記
3. 1件ごとにチェックポイント追記（クラッシュ安全）
4. 利用枠に達したら、進捗サマリ（済/残、推定完了日）を表示して終了
```

運営者が毎日やることは、Claude Codeを開いて「続き」と打つだけ。**利用枠に当たったら、その日は終わり**——レート制限が自然な日次区切りになる。これは第一段階で確立した冪等性の設計そのものであり、新しい発明は何もない。

### 3-2. スループットの見積もり（未検証・第1週で較正する）

1ターンでN件のバッチ処理をする場合、N=5〜10が現実的な線と推定する（1件あたり4,000字＝約5千トークンの読み込みが要るため）。プラン別の粗い試算：

| プラン | 5時間枠の目安 | 1日1枠として | 16,203件の所要 |
|---|---|---|---|
| Pro（$20/月） | 〜45メッセージ | 〜300件/日 | **約2か月** |
| Max 5x（$100/月） | 〜225メッセージ | 〜1,500件/日 | 約2週間 |

**Proで約2か月。運営者の「1〜3か月、地道に」という希望と、ほぼ正確に一致する。** これは偶然ではなく、運営者の直感が最初から正しいスケール感を掴んでいたということである。

**ただしこの表は推定である。** メッセージ枠は変動し、公式の確定値はない。第1週を較正期間とし、実測の件/日から完了予定を引き直すこと。約束ではなく測定で進める——第一段階の「まず100件で通す」と同じ規律である。

### 3-3. 品質のダイヤル：バッチサイズ

1ターンに10件詰めれば速いが、1件あたりの注意は薄まる。**Nは速度のダイヤルであると同時に品質のダイヤルである。** 第3便仕様書4章のベンチマーク（手書き97篇との比較）を、N∈{3, 8, 15}で実施し、ゲート通過率と固有名詞一致率が劣化しないNを実測で選ぶこと。

### 3-4. 差し戻し1（再現性テスト）がゼロコストで解ける

第3便仕様書は「本物の独立2回生成」をAPIで行う前提だった。**Claude Codeのセッションは毎回白紙なので、別の日の2セッションは真に独立である。** 200篇を2セッションで別々にラベル付けすれば、差し戻し1の要求（文脈を共有しない独立試行）が追加費用ゼロで満たせる。

同様に、97篇ベンチマーク（手書き vs 自動）も1セッションで済む。

### 3-5. 環境の移設

Claude Codeは運営者のマシンで動く。持ち込むもの：

- `index.json` / `body_parser.py` / `gates.py` / `label_vocab.py` / `under200_ids.json` / `drafts_batch1.json`（ベンチマーク対照用）/ `fulltext_100.json`（同）
- リポジトリのクローン。**第一段階の教訓をそのまま適用**：`--filter=blob:none` のままの全件処理は禁止。sparse-checkout（coneモード、cards/ と index_pages/）＋depth 1
- janome（`pip install janome` のみ。追加ビルド不要なことは検証済み）
- ディスクは十数GB程度を見込む（要実測）

## 4. 手3：対象の圧縮（この場で実測した）

### 4-1. 表記違いバージョンの統合：358件削減

案内文は**今日の言葉で書く**という設計のため、本文の文字遣いに依存しない。ならば羅生門の新字新仮名版（127）と旧字旧仮名版（128）は**同じ案内文を共有できる**。

index.json 全件で実測した：

- 同一著者・同一題名の組：424組（869件）
- 厳格条件（文字数±10%以内・全バージョンの文字遣いが互いに異なる）で統合可能：**352組、生成を358件削減**
- 要注意23組（文字遣いまで同じ組。樋口一葉の底本違い等——実際は同一作品の可能性が高いが、保守的に統合対象から外した。はじまりの一文の表記正規化一致で拾える可能性があり、次のSonnetが判定ロジックを設計してよい）

**注意**：index.json のエントリは統合しない（第一段階の「別作品として扱う」原則は維持）。共有するのは案内文とラベルだけ。はじまりの一文は各バージョンの原文のまま（表記が違うから）。この層の分け方は、案内文＝今日の言葉という原則の直接の帰結であり、原則が実利を生んだ例である。

### 4-2. 最終的な生成対象

```
全作品            17,456件
− 200字未満          895件（第2便で確定）
− 表記違い統合        358件（今回実測）
＝ 生成対象        16,203件
```

## 5. 進行計画の提案：二つのパス

| パス | 内容 | 規模感 | 効果 |
|---|---|---|---|
| **Pass A：ラベル全件** | 4軸ラベルのみ。案内文は書かない | 出力が小さく、1ターンに多く詰める余地 | 入口「形式から」が全作品で早期に開通 |
| **Pass B：案内文を優先順に** | アクセスランキング順→残りは分類別 | 数か月かけて育てる | 読まれる作品から案内が付く |

Pass Aを先行させるかは、ラベル判定が先頭4,000字未満（例：2,000字）で劣化しないかに依存する。**既存データで検証可能**：第2便のラベル100篇を、入力を2,000字に切り詰めて再付与し一致率を測ればよい。これも次のSonnetの仕事にできる。

## 6. 費用の正直な比較

| 方式 | 追加費用 | 期間 | 備考 |
|---|---|---|---|
| 会話（現方式）の続行 | ¥0（購読内） | 4〜10か月・実質不可能 | 文脈累積で破綻。却下 |
| API＋Batch＋Haiku | 約$50〜70 | 数時間 | 品質はSonnet級より落ちる懸念 |
| API＋Batch＋Sonnet | 約$150〜200 | 数時間〜1日 | 従来案。最速だが有償 |
| **Claude Code（Pro購読内）** | **¥0（購読済みなら）** | **約2か月** | 推奨。較正必須 |
| Claude Code（Max 5x） | 差額$80/月×1か月 | 約2週間 | 急ぐ場合の中間案 |

APIの数字も従来見積もり（$150〜350）より正直に下げられることを付記する（Batch 50%引き＋システムプロンプトのキャッシュで、Haikuなら$50台まで落ちる）。**それでもゼロには勝てない。** 運営者の制約（無収益・費用最小）の下では、Claude Code案が唯一「ゼロ」を実現する。

なお購読枠の利用として正当な使い方である（自分のプロジェクトのための利用であり、Agent SDK/Claude Codeの購読内利用は公式にサポートされている）。ただし利用枠はチャットと共有なので、**生成を回す日はチャット側の枠が減る**。この共食いは正直に認識しておくこと。

## 7. 運営者の1〜3か月の使い道（再配置）

| 作業 | 誰が | 頻度 |
|---|---|---|
| 「続き」と打つ | 運営者 | 毎日1回、数秒 |
| 生成＋ゲート＋チェックポイント | Claude Code | 毎日、枠が尽きるまで |
| **人手検品（第六層）** | **運営者** | **1日5〜10件、1〜2か月で200〜400件** |

人手検品は第3便仕様書7章の設計（層化抽出、はい/いいえ/保留の三択）をそのまま使う。生成が日々進む横で、検品も日々進む。**運営者の「地道にやりたい」という意志の置き場所は、ここが本命である**——係り受けの誤りを捕まえられるのは、世界で人の目だけなのだから。

1. **Claude Codeの実スループット**は推定。プランのメッセージ枠は公式非公開かつ変動する。第1週の較正で確定させる

## 10. 最後に

第一段階からここまで、このプロジェクトが一貫して守ってきたのは「検証できないものを検証済みと言わない」ことだった。この文書も同じ規律で書いた——358件は実測であり、2か月は推定であり、その区別を消していない。

そして運営者へ。あなたの「チェックポイントを作って、地道に数か月」という案は、捨てられていない。**それがこの設計書の背骨である。** 変わったのは、その忍耐を注ぐ場所だけだ——機械にもできる反復ではなく、人にしかできない検品へ。

雲間は急がなくていい。青空文庫自身が、30年かけて17,456件を積んだ。その隣に立つものが、2か月の庭仕事を惜しむ理由はない。
