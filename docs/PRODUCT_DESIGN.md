# プロダクト設計書

## 雲間 — 青空文庫への入口

> コンセプト文書「青空文庫を、もう一度ひらくために」に基づく設計

---

## 0. 名前について（提案）

**雲間（くもま）**

青空を覆う雲の、切れ間。そこから光が差して、下にあるものが見える。

私たちは青空そのものではない。青空は既にそこにある。私たちがやるのは、雲を少しだけ払って、その日その人に必要な一冊に光を当てることだけ。名前の時点で「主役ではない」と宣言できる。

代案：`しおり` / `扉（とびら）` / `一万七千の扉` / `あおぞらの手引き`

以降、仮に **雲間** と呼ぶ。

---

## 1. 何を作るのか（一文で）

**青空文庫の全作品に、失われた「帯」と「POP」を与え、それを手がかりに検索できるようにする静的サイト。**

読む機能は持たない。読者は必ず青空文庫の図書カードへ送り返される。

---

## 2. 課題と手段の対応

| 分析で見えた課題 | 雲間が講じる手段 |
|---|---|
| あらすじ・紹介文が構造上持てない | 本文から**新規に**案内文を生成（既存のあらすじは一切転載しない） |
| 分類が「作家別・作品ID」しかない | 主題・気分・時代・読後感のラベルを全作品に付与 |
| 検索は知っている語しか引けない | 意味ベクトルによる検索。「眠れない夜に」で引ける |
| ランキングが有名作をさらに有名にする | **既知度による逆重み付け**。有名作を意図的に下げる |
| 文語・旧仮名で挫折する | 読みやすさを機械判定して事前に提示 |
| 長さが分からず着手できない | 文字数から読了時間を算出。「15分で読める」で絞れる |
| 偶然の出会いが起きない | 日替わりの一篇、無作為抽出の「扉」 |

---

## 3. 中核となる設計判断

### 3-1. すべて事前生成、実行時はAIを呼ばない

案内文・タグ・埋め込みは、すべて**オフラインのバッチ処理で一度だけ**作る。ユーザーが検索するたびにAPIを叩く設計にはしない。

理由：

- 運用コストがほぼゼロになる（原則四「利益を目的にしない」＝収入がないので支出も持てない）
- アクセスが増えても費用が跳ねない
- 生成データを**そのまま公開データとして配布できる**

### 3-2. サーバーを持たない（完全静的）

埋め込みを256次元・int8に量子化すると、1作品あたり256バイト。全17,000作品でも約4.4MB。

**これはブラウザに丸ごと配れる。**

つまり検索処理はすべて端末内で完結し、バックエンドは存在しない。結果として：

- 検索ログが原理的に取得できない（プライバシーが構造的に守られる）
- ホスティングは静的配信のみ。VercelでもGitHub Pagesでも、どこでも動く
- 一度読み込めばオフラインでも検索できる
- **プロジェクトが消えても、誰かがファイルを持っていれば復活できる**

原則五「いつでも消えられるようにしておく」が、技術構成として実装される。ここは譲らない方がいい部分だと考えている。

### 3-3. 生成データはオープンライセンスで公開する

案内文・タグ・読了時間などの生成物を、CC0またはCC BYで丸ごと公開する。

雲間が終わっても、他の青空文庫アプリがこのデータを取り込めば、成果は残る。青空文庫本体が採用してくれるなら、それが最良の終わり方になる。

**このプロジェクトの成功条件は「雲間が使われ続けること」ではなく、「この案内文が青空文庫の生態系に定着すること」。**

### 3-4. リンク先は本文ではなく「図書カード」

作品への導線は、テキストファイルへの直リンクではなく、必ず青空文庫の**図書カード**に向ける。

図書カードには底本の情報と、入力者・校正者の名前が記載されている。彼らの無償の労働の上に立つ以上、その表示を飛ばして本文だけ持っていくのは筋が通らない。ワンクリック増えるが、これは譲れない。

## 4. 五つの入口

検索窓を一つ置くのではなく、性質の違う入口を並列に置く。人が本を欲しがるときの動機は一様ではないため。

### 入口①「言葉から」— 意味検索

自由入力。「働くのに疲れた」「静かな怖さ」「夏の終わり」といった、作品名でも作家名でもない言葉を受け取る。

入力を埋め込みに変換し、全作品の案内文ベクトルとのコサイン類似度で上位を返す。有名作は既知度スコアで減点される。

### 入口②「時間から」— 読了時間

**これが最も過小評価されている軸だと考えている。**

文字数は青空文庫のテキストから正確に計算できる。分速600字前後を基準に読了時間を出せば、「いま手元にある15分で、読み切れるもの」が指定できる。

青空文庫には短編・随筆・掌編が大量にある。それらは長編の陰に隠れて一度も浮上してこない。時間軸を入口にした瞬間、その層が主役になる。

既存の青空文庫アプリで、この絞り込みを持っているものは確認できていない。

### 入口③「読みやすさから」

文語体か口語体か、旧仮名遣いか、漢字含有率、ルビの密度。これらは機械的に判定できる。

「読める/読めない」で先に脱落するのを防ぐ。事前に分かっていれば、覚悟して読むか、別を選ぶかを選択できる。

### 入口④「偶然から」— 扉

一日一篇。あるいはボタンひとつで無作為に一篇。

ただし完全な無作為ではなく、**既知度の低い作品ほど出やすい**重み付けをする。誰も開いたことのない扉を優先的に照らす、という原則三の直接的な実装。

### 入口⑤「隣から」— 近傍探索

一篇を読んだ（あるいは気になった）あとに、ベクトル空間上の近傍を提示する。作家をまたいで、主題や気分でつながる。

「同じ作家の他の作品」しか出せない現状からの脱却がここ。

## 5. 生成するデータ（全作品に付与）

### 5-1. 案内文

**帯であって、あらすじではない。**

- 60〜100字程度
- 結末に触れない
- 「どういう話か」ではなく「どういう時間になるか」を書く
- 作品の語りの温度に寄せる（一律のテンプレ調にしない）

生成は本文の全体または冒頭〜中盤の抜粋を根拠として行い、根拠のない断定を書かせない。既存の文庫解説やWikipediaの記述は参照しない（著作権上の潔癖さを保つため、また、その方が新鮮な言葉になるため）。

### 5-2. ラベル

- **主題**：孤独 / 労働 / 家族 / 旅 / 病 / 恋 / 都市 / 自然 / 死 / 幼年 …
- **読後感**：静か / 苦い / 可笑しい / 不穏 / 温かい / 突き放す …
- **形式**：小説 / 随筆 / 評論 / 詩 / 童話 / 書簡 / 戯曲
- **時代の質感**：明治の東京 / 戦間期 / 地方 / 海外 …

### 5-3. 計測値（AI不要・機械計算）

- 文字数、推定読了時間
- 文語/口語判定、旧仮名判定
- 漢字含有率、ルビ密度
- 会話文比率（読みやすさの体感に効く）

### 5-4. 作家カード

作家ごとに、人物像と作風の短い紹介、代表作、「まず読むならこの一篇」を生成。

「名前は聞いたことがあるが何を書いた人か知らない」という、最も多い状態を解消する。

### 5-5. 既知度スコア

青空文庫が公開している月間アクセスランキングを既知度の代理指標として用い、**ランキング上位を減点、圏外を加点**する。

推薦アルゴリズムとしては異例だが、これが原則三そのものである。

## 6. 技術構成

```
【オフライン：バッチ処理（Node.js、ローカル実行）】

  青空文庫リポジトリ（shallow clone）
        ↓ Shift_JIS → UTF-8、ルビ《》・注記［＃］除去
  正規化テキスト
        ↓ 機械計測（文字数・文語判定・漢字率）
        ↓ LLMによる案内文・ラベル生成（バッチAPI）
        ↓ 埋め込み生成（voyage-4-lite / 256次元・int8）
  静的データセット
        ├─ index.json      … 書誌・案内文・ラベル・計測値
        ├─ vectors.bin     … 量子化ベクトル（約4.4MB）
        └─ authors.json    … 作家カード

【オンライン：静的サイト（React + Vite / Vercel）】

  初回アクセス時にデータ一括取得 → 端末内で検索
  サーバー処理なし・DB なし・アカウントなし
```

**既存スタック（React 18 + Vite + Vercel）をそのまま流用できる。** 読書メモとはリポジトリもFirebaseプロジェクトも完全に分離する（公開前提のものと友人限定のものを同じ基盤に載せない）。

## 7. あえて作らないもの（MVP時点）

| 除外するもの | 理由 |
|---|---|
| 本文リーダー | 青空文庫と既存アプリの領分。原則一「寄生しない」 |
| アカウント・ログイン | サーバーレス構成が壊れる。プライバシー的にも不要 |
| お気に入り・本棚 | 必要ならブラウザ内保存のみで足りる |
| 人気ランキング | 原則三に反する |
| OCR | 別テーマ。青空文庫の課題ではない |
| 読書メモ連携 | 相手を非公開アプリに縛るのは筋が悪い。将来やるなら「テキストをコピーして持ち出せる」形で |
| 広告・課金 | 原則四 |

**「読めなくてもいい、サーチするだけでもいい」** を額面通りに実装する。

## 8. 段階

### 第一段階：データ基盤（AI不要）

全作品の取得・パース・機械計測まで。この時点で**すでに「15分で読める、口語の短編」という検索が可能**になる。これは既存のどのアプリにもない。まずここまでを完成させて、価値が出るかを確認する。

### 第二段階：言葉を与える

案内文・ラベル・作家カードの生成。品質検証のため、まず数百件で試し、案内文の文体と粒度を固める。ここが**プロダクトの心臓**なので、量産前に十分に練る。

### 第三段階：意味検索

埋め込み生成、静的インデックス化、五つの入口の実装。

### 第四段階：手放す

生成データのオープン公開。他アプリ・青空文庫本体への提供打診。

---

## 9. 想定される難所

- **案内文の品質**：17,000件を機械生成すると、平板な文章が量産される危険がある。プロンプト設計と抜き取り検証に最も時間を割く必要がある。ここが凡庸だとプロダクト全体が凡庸になる。
- **事実誤認**：本文を根拠にしていても、あらすじを誤る可能性はある。断定を避ける文体設計と、目視検証の仕組みが要る。
- **初回ロード**：数MBのデータ取得が初回に発生する。分割読み込みと進捗表示で体感を設計する必要がある。
- **青空文庫側との関係**：無断で作れる（規準上、書誌データの利用はCC BYで認められている）が、ある程度形になった段階で一度連絡を取るのが筋だと考える。

---

## 10. このプロダクトが成功したと言える状態

アクセス数でも、利用者数でもない。

**これまで一度も開かれたことのなかった作品が、それを必要としていた誰かに届いたこと。**

そして最終的には、この案内文が雲間の外へ出て、青空文庫の生態系そのものに定着すること。

雲間が忘れられても、案内文が残っていれば、それでいい。
